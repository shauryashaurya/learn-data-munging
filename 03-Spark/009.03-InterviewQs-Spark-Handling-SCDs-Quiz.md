# Slowly Changing Dimensions (SCDs)                    
                    
Breaking down Slowly Changing Dimensions (SCDs) - something you'll definitely encounter if you work with data warehousing for any length of time.          
          
## What are SCDs anyway?          
          
In data warehousing, dimensions give context to your business processes or facts. Think customers, products, employees, locations, dates - that sort of thing. While some attributes don't change (like date of birth), others change over time, but not super frequently. These are what we call "Slowly Changing Dimensions." Examples include a customer changing their address, a product's price being updated, an employee switching departments, or a new manager taking over a sales territory.          
          
## Why SCDs can be a headache          
          
Working with SCDs introduces several challenges:          
          
1. **Historical accuracy vs. current state:** Do you want reports to show dimension attributes as they were *when a transaction happened* (historical accuracy), or as they are *right now*? This decision drives which SCD type you'll choose.          
          
2. **ETL/ELT complexity:** You'll need more complex transformation processes than with simple dimension loads. You have to:          
   * Spot new dimension members          
   * Find existing members with changed attributes          
   * Apply your chosen strategy (overwrite, new row, new column, etc.)          
   * Handle keys (natural vs. surrogate)          
   * Deal with effective dates or status flags          
          
3. **Storage concerns:** Strategies that keep history (like Type 2) need a lot more storage for dimension tables, since you're adding new rows instead of just updating existing ones.          
          
4. **Query complexity:** Querying historical data often means filtering on effective date ranges or status flags, making queries more complex than with simple dimension tables.          
          
5. **Performance hits:** Larger dimension tables and more complex query logic can slow things down. Joins between big fact tables and historically large Type 2 dimension tables need careful optimization.          
          
6. **Key management:** Type 2 SCDs require surrogate keys (system-generated IDs for each *version* of a dimension row) alongside natural keys (the business identifier). Managing the relationship between these keys is crucial.          
          
7. **Change detection:** You need efficient ways to detect *which* attributes have changed between the source system and the warehouse. Hashing techniques or comparing specific columns are common approaches.          
          
## The SCD Types You'll Run Into          
          
Several types exist, with these being the most common:          
          
* **Type 0 (Fixed / Retain Original):** Set it once, never change it. Any source system changes get ignored. Great for things like "Date of Birth" or "Original Hire Date".          
          
* **Type 1 (Overwrite):** Just replace the old value with the new one. No history kept. Simple but loses all historical context. Works when history doesn't matter (like fixing a typo in someone's name).          
          
* **Type 2 (Add New Row):** This is the most common way to track history fully. When something changes, mark the current row as expired/inactive (by setting an `end_date` or changing an `is_current` flag), then insert a *new* row with the updated values marked as current. You'll need:          
   * A **surrogate key** for each *version* of the dimension row          
   * The **natural key** as the business identifier          
   * **Effective date/time columns** to show when each version was valid          
   * A **current indicator flag** for easy filtering          
          
* **Type 3 (Add New Column):** Keep limited history by adding columns for "previous" values. If a customer's address changes, you might have `current_address` and `previous_address`. When a change happens, the current value moves to previous, and the new value becomes current. This only tracks the *most recent* change though.          
          
* **Type 4 (Mini-Dimension):** Split frequently changing attributes into a separate "mini-dimension" table. The main dimension holds a foreign key to the current version in the mini-dimension. Track history in the mini-dimension, often using Type 2 approach.          
          
* **Type 6 (Hybrid):** Combines techniques. Typically uses Type 2 for history (new rows), but also updates a "current value" column on *all* historical rows (Type 1 + Type 3 behavior). This lets you easily report on current values while preserving historical values.          
          
## Handling SCDs in Spark (and other distributed systems)          
          
1. **Know your business requirements:** Understand how much history you need for each attribute. Not everything needs Type 2 - use Type 1 or 0 where appropriate to simplify things.          
          
2. **Use DataFrame operations effectively:**          
   * **Joins:** `left_outer`, `full_outer`, `inner` joins help compare source data with existing dimension tables          
   * **Conditional logic:** `when()`, `otherwise()` help apply different logic based on whether records are new, changed, or unchanged          
   * **Window functions:** `lag()`, `lead()`, `row_number()` with `partitionBy(...) orderBy(...)` are super useful for Type 2, helping identify previous/next states          
   * **Unions:** `unionByName()` combines datasets representing new records, updated old records, and unchanged records          
          
3. **Generate surrogate keys wisely:** Use functions like `monotonically_increasing_id()` or combine with `row_number()` over a window partitioned by natural key.          
          
4. **Handle effective dating:** Use current timestamp functions or batch processing dates for setting `start_date` and `end_date`. Be consistent with timezones.          
          
5. **Leverage CDC if possible:** If your source system provides Change Data Capture info, use it to avoid full table comparisons.          
          
6. **Use hashing for change detection:** Create a hash of all SCD-monitored columns in source and target. Comparing one hash value is faster than comparing multiple columns.          
          
7. **Optimize your joins:**          
   * Ensure join keys are correctly typed and well-distributed          
   * Use broadcast joins when one side is much smaller          
   * Partition dimension tables thoughtfully on the storage layer          
          
8. **Make it idempotent:** Design your SCD process so running it multiple times with the same source data produces the same result.          
          
9. **Consider modern data lake platforms:** Delta Lake, Hudi, and Iceberg offer features that make SCD implementation easier:          
   * **`MERGE INTO`:** Provides atomic upsert/delete capabilities perfect for SCD logic          
   * **Time Travel:** Query the dimension table as it existed at a previous point          
   * **Schema Evolution:** Helps manage schema changes over time

Which PySpark operation is most central to updating existing customer emails and inserting new customers?

3.  Customers in both -> UPDATE logic (overwrite dimension email with source email).                    
Option A simply concatenates; B finds only new customers; D is just a filter.

Which PySpark function is commonly used for generating unique keys, acknowledging potential limitations?

**Answer:** B

* D: Generating UUIDs is another valid approach for global uniqueness but often done via UDFs or potentially built-in functions in newer Spark SQL versions. `monotonically_increasing_id()` is a more classic Spark approach.

**Q6 (MS):** When implementing SCD Type 2 using Delta Lake's `MERGE INTO` command, which clauses/actions are typically used to handle the logic correctly? (Select ALL that apply)                    
                    
* A) `WHEN MATCHED AND source.change_hash <> target.change_hash THEN UPDATE SET target.is_current = False, target.end_date = current_timestamp()`                    
* B) `WHEN MATCHED AND source.change_hash <> target.change_hash THEN INSERT *` (where * represents source columns mapped to target schema with new SK, dates, flag)                    
* C) `WHEN NOT MATCHED THEN INSERT *` (where * represents source columns mapped to target schema with new SK, dates, flag)                    
* D) `WHEN MATCHED THEN DELETE`                    
* E) An `INSERT` action within the `WHEN MATCHED` clause to insert the *new* version after updating the old one.                    
                    
**Answer:** C, and implicitly the logic described in E (achieved via MERGE mechanics).                    
**Justification:**                    
* C: `WHEN NOT MATCHED THEN INSERT` is essential for inserting dimension members whose natural keys are not yet in the dimension table. In a common SCD Type 2 pattern using MERGE with a prepared source (staging), this clause also handles the insertion of the *new version* of an *existing* natural key.                    
* E: When a change is detected (`WHEN MATCHED AND <change_condition>`), the MERGE statement needs to perform two logical actions: expire the old record (typically via an `UPDATE SET is_current=False, end_date=now()`) and insert the new record (often handled by the `WHEN NOT MATCHED THEN INSERT` clause by including the new version in the prepared source data). So, while not a direct `INSERT` clause *within* the `WHEN MATCHED`, the *result* of a match triggering a change involves an insertion.

**Q8 :** Consider using PySpark Window functions for SCD Type 2. You have a DataFrame `all_versions_df` containing all historical versions for each `natural_key`, ordered by `change_timestamp`. Which window function helps determine the `end_date` for each version based on the `start_date` of the *next* version for the same `natural_key`?                    
                    
* A) `row_number().over(Window.partitionBy("natural_key").orderBy("change_timestamp"))`                    
* B) `rank().over(Window.partitionBy("natural_key").orderBy("change_timestamp"))`                    
* C) `lead("change_timestamp", 1).over(Window.partitionBy("natural_key").orderBy("change_timestamp"))`                    
* D) `lag("change_timestamp", 1).over(Window.partitionBy("natural_key").orderBy("change_timestamp"))`                    
                    
**Answer:** C                    
**Justification:** The `lead()` function looks ahead within a partition. `lead("change_timestamp", 1)` retrieves the `change_timestamp` (which is the start time) of the *next* row within the window partitioned by `natural_key` and ordered by time. This timestamp is typically used as the `end_date` for the *current* row (often subtracting a small interval like 1 second or 1 day depending on granularity). `lag()` looks backward. `row_number()` and `rank()` assign sequence numbers.

**Q9 :** Your SCD Type 2 process in PySpark needs to be idempotent. If the job processes the exact same batch of source data twice, the final dimension table state must be identical to the state after the first successful run. Which factors are most critical to ensure idempotency? (Select ALL that apply)                    
                    
* A) Using `monotonically_increasing_id()` for surrogate keys.                    
* B) Basing `start_date` and `end_date` logic strictly on source data timestamps or a deterministic batch identifier/timestamp, rather than `current_timestamp()` executed during the run.                    
* C) Using `hash()` for change detection.                    
* D) Carefully handling the join condition between source and dimension to avoid re-inserting duplicates or incorrectly re-expiring already expired records.                    
* E) Using Delta Lake's `MERGE INTO` with appropriate conditions.                    
                    
**Answer:** B, D, E                    
**Justification:**                    
* A: `monotonically_increasing_id()` is non-deterministic; running the job again might assign different SKs, violating strict idempotency if SKs need to be stable across reruns (though the *logical* state might be recoverable). Deterministic SK generation (e.g., hashing key+timestamps) might be needed for strict idempotency.                    
* B: Using `current_timestamp()` can lead to different start/end dates on reruns. Basing dates on source data or a fixed batch time ensures consistency.                    
* C: Hashing itself is deterministic, so it helps, but it doesn't guarantee idempotency alone; the logic using the hash comparison must be idempotent.                    
* D: The core logic must correctly identify records that have *already* been processed in a previous identical run and not apply changes again. This involves precise join conditions (e.g., joining source only to `is_current=True` records) and potentially checking timestamps.                    
* E: Delta Lake's `MERGE` provides atomicity and its conditional logic, if designed correctly (like checking timestamps or hashes within the `WHEN MATCHED` condition), can be made idempotent. It prevents partial updates that might occur in non-atomic DataFrame operations.

**Q11 (MS):** You are implementing SCD Type 2 in PySpark. You notice data skew during the join between the large dimension table (`dim_df`) and the incoming source data (`source_df`) on `natural_key`. Which strategies could potentially mitigate this skew? (Select ALL that apply)                    
                    
* A) Broadcasting `source_df` if it's small enough.                    
* B) Salting the join key (`natural_key`) in both DataFrames by appending a random/hash-based suffix and adjusting the join condition.                    
* C) Repartitioning `dim_df` using `dim_df.repartition(N, "natural_key")` before the join.

**Answer:** A, B, C, D

* C: Repartitioning the larger DataFrame by the join key can help ensure data is distributed better before the shuffle, although it might not fully resolve skew if one key is extremely dominant. **Q23 :** When joining a large fact table (`fact_df`) to a large SCD Type 2 dimension table (`dim_df`) in PySpark to get the historically accurate dimension attributes corresponding to each fact's timestamp (`fact_ts`), what is the typical join condition?                    
                    
* A) `fact_df.natural_key == dim_df.natural_key AND dim_df.is_current == True`
